# 效能：整體幀率低

使用者描述（2026-11-16）：整體幀率低，不是規律頓挫，也不是只在轉視角時卡。

## 資料來源

沒有新的遊戲測試。用的是 session 28～61 已有的 `runtime.jsonl`（僅本機）：
`runtime_counters` 事件約每 5 秒一筆，含 `frames`、`composite_frames`、`compositor_ticks`、`qpc_frequency`、`tick_ms`。

- 幀率 = `frames` 的差 ÷ `tick_ms` 的差。
- 合成時間 = `compositor_ticks` 的差 ÷ `qpc_frequency`。計時範圍是 `Engine::compose` 裡鎖定後備緩衝區、寫入像素、解鎖這一段（`engine.cpp` 的 `paint_surface` 呼叫前後）。

全部是 Steam 私人副本、視窗模式 1600×1200、DX7 渲染器。各場的場景和操作不同，不是對照實驗。

## 發現

| 等級 | 內容 |
| --- | --- |
| CONFIRMED | 每合成一幀要 5.7～9.5 ms，各場都在這個範圍，和畫了多少無關（每幀只寫幾千個像素）。 |
| CONFIRMED | 體力／法力數值、飄字、敵人血條加入後（session 35 起），有合成的幀從 3% 升到 50～100%，合成占掉 20～33% 的時間。 |
| STRONG EVIDENCE | 這是幀率低的主要原因之一。同一存檔的二分測試：session 51（三個功能關）73.9 fps；session 52（開）47.5 fps；session 54（只計算不畫）83.8 fps。 |

## 使用者確認（2026-11-16）

在首頁關掉三個勾選框後，使用者回報「確實有差別」。主觀觀察，沒有數字。

## 縮小鎖定範圍大概沒用（STRONG EVIDENCE）

session 28、29、51 幾乎只有對話和標籤要合成（鎖定範圍是一兩行字），每幀仍要 7.9～9.5 ms，
和橫條加血條幾乎鎖整個畫面的場次（5.7～8.3 ms）沒有差別。成本看起來是每次鎖定固定的，和範圍無關。
所以「分成幾個小區域鎖定」不會比較快，鎖定次數變多反而可能更慢。這個實驗不做了。

## 計時拆分（已加入，尚未進遊戲量測）

`runtime_counters` 多了三個欄位，都是唯讀計時，不改變行為：

- `lock_ticks`：花在表面 Lock 呼叫裡的時間。
- `unlock_ticks`：花在 Unlock 呼叫裡的時間。
- `locked_pixels`：鎖定矩形面積的總和。

`compositor_ticks` 扣掉前兩者就是寫入像素的時間。量到之後才知道時間是花在讀回（Lock）還是傳上去（Unlock）。

## session 62 量測結果（2026-11-16，CONFIRMED）

Steam 私人副本、視窗模式 1600×1200、三個功能開、代理載入。90 秒、2,659 個合成幀（100% 的幀都合成）、
平均 29.5 fps、錯誤 0、例外 0。結束後副本已還原並通過檢查。

| 每個合成幀 | 時間 | 占總時間 |
| --- | --- | --- |
| Lock | 8.71 ms | 25.7% |
| 寫入像素 | 0.27 ms | 0.8% |
| Unlock | 不到 0.01 ms | 0.0% |

- 合成時間的 97% 在 Lock 呼叫裡。我們自己畫字的成本可以忽略。
- 和面積無關：只鎖 0.02 百萬像素（橫條上的數字）時 Lock 要 8.5～10.5 ms；鎖 0.5～0.9 百萬像素時 7.3～8.2 ms。
- Unlock 幾乎立刻返回。包裝層可能把上傳延後到之後的繪製或 Flip，那部分成本不在我們的計時內（HYPOTHESIS）。
  同一存檔 session 54（不畫）有 83.8 fps，這場只有 29.5 fps，差距比 Lock 的 25.7% 大；場景不同，不能直接相減。

結論：要改善就得讓常駐的顯示不經過後備緩衝區的 Lock。調整鎖定範圍、次數或我們的繪字程式都沒有用。

## 方案 B：經 Direct3D 裝置繪製（使用者授權 2026-11-16）

`runtime/U9ChtRuntime/gpu_overlay.h`／`.cpp`，測試 `U9ChtGpuOverlayTests`。

- 裝置：`[backend+0x3FC3BC]`，遊戲在 `0x59A0CA`～`0x59A0D4` 用它呼叫 EndScene（vtable +0x18）。
  靜態反組譯加 session 63 實際呼叫成功（CONFIRMED）。
- 做法：字形覆蓋率寫進一張 1024×1024 ARGB 貼圖；每個繪製指令變成一個螢幕座標矩形，顏色取指令的顏色、
  alpha 取貼圖。在遊戲的 EndScene 之後、Flip 之前自己 BeginScene／DrawPrimitive／EndScene。
- 會動到的 14 個 render state、12 個 texture stage state、第 0 層貼圖、viewport，都先讀出、畫完還原。
- 沒有新的遊戲 hook，沒有改 `u9.exe` 位元組。
- 開關：預設開啟（2026-11-17 起，使用者決定）。在中文化資料的 `runtime/` 資料夾放 `gpu_overlay.off` 可強制走鎖定路徑。
  session 63、64 當時是用 `gpu_overlay.on` 啟用的實驗版。
- 退回鎖定路徑的情況：游標等原生圖形壓在中文字上（需要逐像素遮罩）、任何一步失敗。
  連續失敗 8 次、發生例外或狀態還原失敗就整場停用。

### session 63 結果（CONFIRMED，數字部分）

Steam 私人副本、視窗模式 1600×1200、三個功能開。425 秒、23,369 幀，錯誤 0、例外 0，副本已還原。

| 項目 | 數值 |
| --- | --- |
| 走 Direct3D 的幀 | 19,362 |
| 退回鎖定的幀 | 2,895（全部是遮罩情況；失敗 0） |
| 狀態還原失敗 | 0 |
| Direct3D 路徑每幀 | 0.2～1.1 ms，多數約 0.6 ms（鎖定是 8.7 ms） |
| 占總時間 | Direct3D 2.5%、鎖定 5.5% |
| 平均幀率 | 54.5（session 62 是 29.5；場景不同） |
| 貼圖內字形 | 349 個，沒有重排 |

- 純走 Direct3D 的區段，幀率仍在 30～120 之間隨場景變化，所以剩下的低幀率來自別處（遊戲本身或其他成本）。
- 退回鎖定的區段幀率明顯較低（約 35～45）。要再改善，下一步是讓遮罩情況也不必鎖定。
- 使用者目視確認（2026-11-16）：中文都在（橫條數字、血條、飄字、對話、物品名稱）；字沒有模糊、偏移、
  變色或方框；遊戲畫面沒有異常；體感「有好一些」。

### 遮罩情況改用條狀矩形（已實作，尚未進遊戲驗證）

游標壓在中文字上時，舊路徑逐像素跳過被蓋住的點（`OccluderMask::hides`）。新路徑現在把這種字切成
橫向條狀矩形（`gpu::emit`），用同一個 `hides` 判斷，相鄰且可見區段相同的列合併成一條。
單元測試逐像素比對：條狀矩形涵蓋的像素和舊路徑會寫入的像素完全相同、不重疊。
一列超過 16 段或頂點不夠時，那一幀仍退回鎖定（計數 `gpu_masked_frames`）；用到條狀的幀計在 `gpu_strip_frames`。
